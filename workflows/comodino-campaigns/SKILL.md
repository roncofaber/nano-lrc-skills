# CoMoDInO campaigns on Lawrencium

CoMoDInO (github.com/roncofaber/comodino, private: ask the maintainer for access; package and imports `comodino`) owns the recipes, generators, chain runner and campaign layout, and ships no site material. Its `docs/workflows/campaign_runbook.md` is the single ordered procedure from decisions to analysis, with exact commands and gates; follow it and do not re-derive the pipeline here. Its `skills/comodino/SKILL.md` covers the science. This skill supplies only what the runbook leaves to the site: modules, environment, launcher, resources, scheduler scripts. [references/comodino.md](references/comodino.md) maps runbook steps to Lawrencium specifics.

Below, `CHECKOUT` is your comodino clone and `ENV` your Python env with editable comodino and mdinterface installs (for example `$HOME/miniforge3/envs/mdinterface`). The job scripts read the env's `bin/` from `ENV_BIN`.

### Sources of truth and defaults for a new campaign

- Before creating anything for a new campaign, run the runbook's "Campaign intake": ask its questions, show its Defaults and the site defaults below for confirmation, and offer only the systems it lists as supported. Site questions to add: allocation (default `nano` on etna) and campaign location under scratch.
- Decide only from the pinned CoMoDInO and mdinterface documentation and code, this skill, `lrc-cluster`, and what the user states when starting the campaign. Do not read other campaign folders, sibling agents' work or old handoffs to make decisions: they are not reviewed defaults, and copying them spreads past mistakes. When the documentation is silent, ask the user or record an open question; do not borrow a value from a neighbouring folder.
- Defaults, used unless the user specifies otherwise at campaign start:
  - Engine: `lammps/20250722u6-gcc`. Record the choice in `decisions.md` once and use that exact module everywhere in the campaign; do not validate or switch to other builds unless asked.
  - LJ mixing rule: Lorentz-Berthelot (`md.mixing: "arithmetic"`) unless the user names a force field that requires another rule (`geometric`, `sixthpower`; needs CoMoDInO with selectable mixing).
  - Replicas, timestep, durations, interface geometry, numbering and every other scientific setting: the "Defaults" section of CoMoDInO's `campaign_runbook.md` (one `r01` per system through unbiased production, 12 walkers only for biased metadynamics, 1 fs with water SHAKE, the example protocols and manifests). `comodino campaign init` pre-fills them in `decisions.md`; cite that section as the review reference.
  - Write each system's sources with `comodino campaign system CAMPAIGN/FAMILY/NN_name`, never by copying example files. It takes parameters from the mdinterface databases, seeds from the folder path and names from the runbook's "System folder names" (e.g. `02_na`, `04_nacl_02pairs`, `02_na_au111`).
  - Coordination-CV cutoffs and exponents are never defaults: bulk preparations run without CVs, then each system's own production RDF gives them (`python -m comodino.md.analysis.cv_proposal`, runbook step 8), the user reviews them, and `comodino campaign observe` applies them in a `02_observe` bundle.
  - Anything CoMoDInO leaves without a default is an open question for the user, never an agent choice.
- The user's instructions at campaign start are the approval for the choices they name. Record them verbatim in `decisions.md` with the date as the review reference; everything else stays `pending` until the user reviews it.

- New campaigns start with `comodino campaign init CAMPAIGN` and must pass `comodino campaign check CAMPAIGN` before every handoff. Scheduler scripts, the launcher file and `slurm-*.out` logs live only in `CAMPAIGN/99_jobs/`; submit from there. Engine validation goes to `CAMPAIGN/00_validation/NN_<engine>/`. Older campaigns keep their own layout; never move active runs. Only `AGENTS.md`, `decisions.md` and the numbered folders may sit at the campaign root: put agent notes, findings and logs in `AGENTS.md` sections, not in extra root files, or `campaign check` fails.
- `comodino` has three installed commands (`resources`, `skill`, `campaign ACTION` with actions init, check, system, seeds, policy, accept, analysis, observe); `python -m comodino.campaign` runs nothing, use the installed command; everything else is a `python -m comodino...` module. Use absolute paths in every runner and generator command: the runbook's relative examples assume the campaign root as working directory.
- Validate the engine first, before building anything (it needs no structures): a broken engine found after building wastes the whole setup.
- Validate each engine once per campaign with [assets/engine_validation.sbatch](assets/engine_validation.sbatch) (runbook step 5): it refuses the broken pre-update3 modules, records module, executable sha256, comodino commit, `lmp -h` and `pip freeze`, runs the native pytest checks with `--basetemp` under `00_validation/`, fails if any test skipped, and optionally runs the `prepare_pilot.py check --smoke` on a bulk structure. It sets `COMODINO_EXECUTION_REFERENCE` (slurm job, module, node), the free-text field CoMoDInO records in place of the removed module/job fields.
- Submit chains with [assets/submit_chain.sh](assets/submit_chain.sh) `BUNDLE [START_STAGE]` from `99_jobs`: it derives a short job name from the bundle path (`<campaign NN><b|i>-<system>-<bundle>`, e.g. `06i-brpt111-p01`, `05b-nacl40p-o02`) and sets RECORDS, CODE and `--comment=mdwatch:stall=30,watch=$BUNDLE`, so mdwatch, if you use it (`lrc-mdwatch`), watches the bundle where LAMMPS writes; without `watch=` every chain would be falsely reported STALLED after 30 minutes.
- Run a preparation chain as one sbatch per bundle through `python -m comodino.md.execution.chain`, never as an agent resubmitting one stage per job. Use [assets/comodino_chain.sbatch](assets/comodino_chain.sbatch); it only loads the module and calls the runner with `CAMPAIGN/99_jobs/launcher.json`, the single launcher file the runbook names (`["mpirun", "--bind-to", "core", "--map-by", "core", "-np", "24", "{engine}"]` for one etna node with the gcc build). Write it once per campaign; the same file serves the login-node `--check-only` and the job, and the job refuses to start if its `-np` differs from `SLURM_NTASKS`. Records, `authorization.json` and `continuation.json` for bundle `FAMILY/NN_system/rNN/NN_name` all live in `FAMILY/NN_system/rNN/records/NN_name/`. Do not write a bespoke chain loop or review script; extend the continuation policy instead.
- Before submitting, run the same runner command with `--check-only` on the login node: it catches a wrong start stage, missing prerequisite reviews, mismatched authorization or policy, and existing outputs, so the job does not burn a queue slot failing in preflight. It stops at the first failing gate only; errors name the file and field (CoMoDInO 6422277+), so fix and rerun until it reports `ready_for_preparation_chain`.
- Continuation policies: start from `comodino campaign policy BUNDLE` (CoMoDInO 6422277+), which writes the pending default into the bundle's records folder. Show it to the user and approve it only on their decision. Minimization must accept both `energy tolerance` and `force tolerance`; the SD+CG minimize on this engine usually ends on energy tolerance.
- Resume by resubmitting with `START_STAGE` set to the first unstarted stage. A stage that was running when the job died cannot be resumed in place: partial logs and restarts block it, and recovery needs a supported procedure or a regenerated bundle (a new numbered sibling, e.g. `03_prepare_dt05fs`).
- A killed job (TIMEOUT, NODE_FAIL, scancel) leaves `<bundle>/.chain.lock`. Confirm the job is gone (`squeue`, or `mdwatch show JOBID`) before deleting it.
- Split long campaigns into phases, one agent each, handing off through the campaign `AGENTS.md`: setup (init, sources, engine validation, builds, bundles, policies, chain submission); after the chains finish, acceptance (step 7); then observation (step 8). One agent driving a whole campaign runs out of context after a few hundred tool calls and stops without reporting.
- Run trajectory analysis (`comodino campaign analysis`, `python -m comodino.md.analysis.cv_proposal`, RDFs) as a short etna sbatch job from `99_jobs`, never on the login node or in the agent's own shell; a CV proposal over production trajectories pins the shared node and hangs every other session on it. Read the resulting `report.json` and CSV files afterwards.
- Never open image files (.png, .pdf) when the agent's model is text-only (CBorg Coder Max); read the analysis `report.json` and CSV files instead.
- Pin the code for the life of a campaign. The runner imports `comodino` at every stage, so pulling `CHECKOUT` while chains run breaks them mid-flight. Create a worktree at the recorded commit (`git -C CHECKOUT worktree add CAMPAIGN/99_jobs/comodino COMMIT`) and pass it as `CODE=`; the job scripts put it first on `PYTHONPATH`, which overrides the editable install. Record the CoMoDInO and mdinterface commits in the campaign `decisions.md`.
- After pulling CoMoDInO, refresh the editable install (`ENV/bin/pip install --no-deps -e CHECKOUT`); otherwise the `comodino` console script keeps its old entry point and fails.
- Never hand-edit or `sed` generated inputs. Any changed setting means a copied protocol JSON and a new bundle.
- A passed continuation review is not physical acceptance; chain completion reports `physical_acceptance="inconclusive"` until the separate scientific review.

## Job-script pitfalls seen on this cluster

- Conda envs have no `bin/activate`. Prepend `ENV/bin` to `PATH` (the job scripts do this through `ENV_BIN`); a script that sources `bin/activate` dies in seconds.
- The CoMoDInO tools are `python -m` modules, not console scripts; only `comodino resources` and `comodino skill` are installed commands.
- The native engine tests finish in about a minute on one etna node; a short pass is expected, not suspicious, as long as none skipped.
